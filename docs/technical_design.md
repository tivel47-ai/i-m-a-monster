# I'm a Monster — Technical Design Document (TDD)
## MVP v0.1 — рабочий технический проект

**Статус:** черновик для первого прототипа  
**Платформа:** Windows PC  
**Движок:** Godot 4.x Stable (точную версию записать после проверки)  
**Язык:** GDScript  
**Связанный документ:** GDD MVP v0.1

> Документ описывает технические решения для первого вертикального среза. Не проверенные прототипом решения остаются предварительными.

## 1. Цель прототипа

Первый прототип должен позволять запустить тестовую карту, выбрать одного зомби щелчком мыши, приказать ему двигаться к точке и увидеть, как он останавливается у цели. Затем добавим препятствие и проверим навигацию.

**Вне рамок первого прототипа:** жители, бой, заражение, группы, способности, кампания, метапрогрессия, финальная графика и сложный UI.

## 2. Технологический стек

| Компонент | Решение |
|---|---|
| Движок | Godot 4.x Stable; точный номер записать в README |
| Язык | GDScript |
| Платформа | Windows |
| Редактор | VS Code и/или встроенный редактор Godot |
| Контроль версий | Git |
| Визуальные заглушки | Простые формы/цветные маркеры |
| Внутреннее разрешение | Предварительно 640×360, 16:9; проверить визуально |
| Навигация | Средства навигации Godot 4, когда дойдём до препятствий |

Не обновлять Godot посреди задачи без причины. Не фиксировать предварительные значения как окончательный баланс.

## 3. Архитектурные принципы

1. Сначала рабочий вертикальный срез, затем расширение.
2. Ввод игрока распознаёт команды; юнит отвечает за своё движение; сцена уровня размещает объекты.
3. Не вводить глобальные Autoload/Singleton без доказанной необходимости.
4. Отделять логику от графики: заглушку должно быть легко заменить спрайтом.
5. Не проектировать заранее системы, которые пока не нужны.
6. Одна задача ИИ — одно небольшое проверяемое изменение.
7. Запускать игру и проверять критерии приёмки после каждого изменения.
8. После успешной проверки создавать Git commit.
9. Не строить новые функции поверх сломанного состояния.
10. TDD должен описывать фактическую реализацию; обновлять его по результатам экспериментов.

## 5. Сцены

### `main.tscn`
Стартовая сцена приложения. На первом этапе содержит экземпляр тестовой карты. Не создавать менеджеры миссий и ресурсов заранее.

### `test_map.tscn`
Тестовая площадка: простой фон, один зомби и позже — препятствия. Карта должна позволять проверить короткое и длинное перемещение. Полноценный тайлсет пока не нужен.

### `zombie.tscn`
Отдельная переиспользуемая сцена одного юнита. В ней будут корневой узел движения, визуальный узел (временная форма или `Sprite2D`), а при необходимости — коллизия и навигационный агент. Точный корневой тип выбрать до написания скрипта движения; не смешивать несколько способов управления юнитом.

## 6. Управление

Предварительные действия:
- **ЛКМ по зомби:** выбрать юнита.
- **ПКМ по карте:** приказать выбранному юниту двигаться к точке.
- **Esc:** снять выбор, если это понадобится в текущей реализации.

На этом этапе поддерживается только один юнит. Выбор группы, атака области и удержание позиции пока не реализуются.

Критерии:
- клик по пустой карте не выбирает зомби;
- ПКМ после выбора назначает новую цель;
- новый приказ заменяет старую цель;
- если юнит не выбран, ПКМ не вызывает ошибку;
- координаты мыши переводятся из экранных координат в мировые, особенно после добавления камеры.

## 7. Движение зомби

### Состояния
- `IDLE` — нет активной цели, зомби стоит.
- `MOVING` — зомби движется к цели.
- При достижении допустимой окрестности цели зомби останавливается и возвращается в `IDLE`. Отдельное состояние `ARRIVED` можно добавить, только если оно действительно потребуется.

### Данные
- текущая позиция;
- целевая позиция;
- скорость;
- допустимое расстояние до цели;
- статус движения.

Начальные числовые значения временные и должны проверяться в игре.

### Ожидаемое поведение
1. При запуске зомби неподвижен.
2. После приказа получает цель и начинает движение.
3. При достижении цели останавливается.
4. Новый приказ во время движения меняет цель.
5. У цели не должно быть дрожания или бесконечного микродвижения.
6. При препятствии зомби должен обходить его навигацией или корректно сообщать о недоступной цели; он не должен проталкиваться сквозь стену.

## 8. Навигация и препятствия

Двигаться по прямой на пустой карте — первый подэтап. Затем:
1. добавить видимый маркер цели;
2. разместить одно препятствие;
3. настроить навигационную область/агента, если выбран этот способ;
4. проверить обход препятствия;
5. проверить цель внутри препятствия или в недоступной области.

Наличие навигационного узла само по себе не доказывает, что путь работает. Проверить поведение в запущенной игре и сверить API с установленной минорной версией Godot 4.

## 9. Поток команды

```text
Ввод мыши
   ↓
Проверка выбранного юнита
   ↓
Получение координат цели в мире
   ↓
Передача приказа зомби
   ↓
Обновление цели движения
   ↓
Движение и остановка
```

Не создавать отдельный `OrderManager`, пока приказ не понадобится нескольким типам юнитов. В будущем могут появиться независимые системы выбора, приказов, боя, заражения, ИИ деревни, миссии и метапрогрессии. Это будущие обязанности, не обязательный список файлов первого прототипа.

## 10. Временная визуализация

- зомби — цветной круг/спрайт-заглушка;
- цель — маркер;
- препятствия — прямоугольники;
- выбранный юнит — контур или другой индикатор.

Финальные спрайты, анимации, эффекты и освещение отложить до проверки основного цикла управления.

## 11. Граничные случаи

Проверить:
- команда без выбранного юнита;
- цель совпадает с текущей позицией;
- новый приказ выдан до завершения предыдущего;
- цель за препятствием;
- цель недоступна для навигации;
- отсутствует ожидаемый узел;
- в сцене случайно нет зомби;
- после добавления камеры экранные и мировые координаты не совпадают.

Невалидный приказ должен обрабатываться предсказуемо: безопасно игнорироваться или приводить к диагностическому сообщению. Не скрывать реальные ошибки пустыми обработчиками.

## 12. План реализации и критерии приёмки

### Этап 0 — среда
Открыть проект из папки репозитория, записать версию Godot, убедиться, что проект импортируется, запустить пустой проект и проверить `git status`.  
**Готово:** проект открывается и запускается без ошибок.

### Этап 1 — главная сцена и карта
Создать `main.tscn` и `test_map.tscn`, назначить главную сцену, добавить простой фон.  
**Готово:** при запуске видна тестовая карта.

### Этап 2 — зомби-заглушка
Создать `zombie.tscn`, добавить временную форму и разместить её на карте.  
**Готово:** зомби виден, ошибок нет.

### Этап 3 — выбор
Реализовать ЛКМ и индикатор выбора.  
**Готово:** юнит выбирается предсказуемо.

### Этап 4 — приказ движения
Реализовать ПКМ, передачу мировой координаты, движение, остановку и смену цели.  
**Готово:** все проверки раздела 7 проходят.

### Этап 5 — препятствия
Добавить препятствие и настроить навигацию.  
**Готово:** зомби не проходит сквозь препятствие и корректно реагирует на недоступную цель.

### Этап 6 — фиксация
Пройти ручные проверки, исправить ошибки, обновить TDD и сделать Git commit.  
**Готово:** прототип можно повторно открыть и запустить из чистого рабочего состояния.

## 13. Работа с ИИ и Git

Каждый запрос ИИ должен содержать контекст игры, текущую цель, имена существующих файлов, требуемое поведение, критерии приёмки и ограничения. Просить перечислить файлы до изменения и объяснить способ проверки после.

Рабочий цикл:
1. проверить `git status`;
2. дать ИИ одну ограниченную задачу;
3. просмотреть изменения;
4. запустить игру;
5. проверить критерии;
6. исправить ошибки;
7. после успеха создать commit.

Не принимать утверждение ИИ «всё работает» без запуска и проверки.

## 14. Первый запрос для ИИ-кодинга

> Работаем над 2D-игрой I'm a Monster на Godot 4 и GDScript. Прочитай `docs/game_design.md` и `docs/technical_design.md`, если они доступны. Сейчас выполняем только этап 1: создать минимальную главную сцену и тестовую карту. Не реализовывай зомби, движение, боёвку, жителей или UI. Используй простую заглушку фона. Сначала перечисли файлы, которые собираешься создать или изменить, затем внеси только необходимые изменения. Не меняй настройки проекта без необходимости. В конце объясни, как запустить сцену и проверить результат. Критерий приёмки: проект запускается и показывает тестовую карту без ошибок.

После успешной проверки этапа 1 отдельной задачей создаётся сцена зомби-заглушки.

## 15. Открытые решения

- точная установленная версия Godot 4.x;
- окончательное внутреннее разрешение и масштабирование;
- нужен ли `Camera2D` на первой карте;
- окончательный способ навигации и столкновений;
- скорость и порог остановки;
- способ приказов для нескольких юнитов;
- поведение при недоступной цели.

Эти вопросы не блокируют пустую тестовую карту. Принимать решение непосредственно перед соответствующим этапом и обновлять документ по результатам тестирования.
