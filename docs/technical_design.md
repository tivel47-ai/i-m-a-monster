## 1. Цель прототипа

Текущий технический прототип содержит тестовую карту с несколькими зомби и жителями, препятствием, одиночным и рамочным выделением, групповыми приказами движения, навигацией, автоматическим агро с проверкой прямой видимости, боем с периодическим обменом уроном и заражением по вероятности при ударе. Несколько зомби одновременно атакуют одного жителя, каждый своим таймером; урон каждого учитывается. Житель заражается с шансом 15% на каждый успешный удар и превращается через 2 секунды после первой успешной проверки. Здоровье, урон и интервал атаки настраиваются в сценах/скриптах. Тестовая карта учитывает завершённые заражения, показывает прогресс и фиксирует победу при заражении 80% жителей.

Полноценная тактическая боевая модель и сложные исходы боя пока не реализованы. Текущая версия содержит упрощённые периодические атаки, проверку заражения при ударе, превращение, смерть, полосы здоровья и маркеры погибших; создаваемый зомби использует общую сцену и систему управления. Следующий приоритет — вручную проверить весь игровой цикл в Godot, а не расширять количество приказов или функций интерфейса.

**Пока вне текущего прототипа:** вероятностное определение сложного исхода боя, броня, оружие, способности, кампания, метапрогрессия, финальная графика и сложный UI.

Для тестовой миссии реализованы учёт жителей и простой экранный индикатор прогресса; полноценная система миссий, поражения и наград не входит в этот этап.

## 3. Архитектурные принципы

1. Сначала рабочий вертикальный срез, затем расширение.
2. Ввод игрока распознаёт команды; юнит отвечает за своё движение; сцена уровня размещает объекты.
3. Не вводить глобальные Autoload/Singleton без доказанной необходимости.
4. Отделять логику от графики: заглушку должно быть легко заменить спрайтом.
5. Не проектировать заранее системы, которые пока не нужны.
6. Одна задача ИИ — одно небольшое проверяемое изменение.
7. Запускать игру и проверять критерии приёмки после каждого изменения.
8. После успешной проверки создавать Git commit.
9. Не строить новые функции поверх сломанного состояния.
10. TDD должен описывать фактическую реализацию; обновлять его по результатам экспериментов.
11. Текущий приоритет — минимальный игровой цикл; дополнительные приказы и интерфейсные функции развивать по мере появления проверяемых игровых ситуаций.
12. Будущая реализация должна различать приказ игрока, навигацию, выбор цели, поведение существа и локальную реакцию на ситуацию. Это разделение ответственности не требует заранее создавать отдельные классы или универсальную систему.

## 5. Сцены

### `main.tscn`
Стартовая сцена приложения, содержащая экземпляр тестовой карты. Не создавать менеджеры миссий и ресурсов заранее.

### `test_map.tscn`
Текущая тестовая площадка содержит простой фон, три экземпляра сцены зомби, четыре экземпляра сцены жителя и физическое препятствие, исключённое из проходимой навигационной области. Расположение объектов предназначено для проверки группового перемещения, агро по нескольким целям, прямой видимости и навигационного обхода препятствия. Полноценный тайлсет пока не нужен.

### `zombie.tscn`
Отдельная сцена зомби с корневым `CharacterBody2D`, временным визуальным узлом, физической коллизией, дочерними `Area2D` для обнаружения кликов и автоматического агро, а также `NavigationAgent2D`.

## 6. Управление

Реализованные действия:
- **ЛКМ по зомби:** выбрать юнита.
- **ЛКМ по пустому месту:** снять выбор.
- **Перетаскивание ЛКМ дальше 8 экранных пикселей:** выделить рамкой пересекающиеся области управляемых существ; новый набор заменяет прежний. Жители не входят в группу управляемых существ и не выделяются.
- **ПКМ по карте:** приказать выбранному юниту двигаться к точке.
- **Shift + ПКМ по карте:** приказать выбранным юнитам распределиться по кругу радиусом 100 игровых единиц.
- Новый приказ ПКМ заменяет предыдущую цель.

В сцене зомби область выбора использует существующий `Area2D`. Одиночный щелчок проверяет эту область, а рамка проверяется как выпуклая форма, преобразованная из экранных координат в мировые через canvas transform; это учитывает смещение и масштаб камеры. Визуальная рамка находится в `CanvasLayer` и игнорирует мышь. Набор выделения формируется только из группы `player_units`.

Рамочное выделение заменяет предыдущий набор; модификаторы Shift/Ctrl не меняют выделение. ПКМ обрабатывается картой один раз, координата преобразуется тем же canvas transform в мировую. Обычная ПКМ передаёт всем выбранным юнитам одну точку. Shift + ПКМ задаёт центр круга, для каждого выбранного живого зомби карта назначает отдельную индивидуальную точку.

Кандидаты создаются детерминированной спиральной выборкой внутри круга, сопоставляются с навигационной областью и проверяются на физическое пересечение с препятствиями и другими невыбранными телами. Маршрут от каждого зомби к точке проверяется средствами NavigationServer2D. При выборе учитывается размер физической формы зомби; если полностью разнесённых точек недостаточно, допускается более плотное размещение без наложения, а оставшиеся юниты отменяют прежний приказ и останавливаются на текущем месте.

После прибытия приказ области завершает движение так же, как обычная команда: зомби останавливается и не корректирует достигнутую точку, затем автоматическое агро возобновляется после обычной задержки 0,3 секунды. Пока зомби не занят преследованием или боем, его по-прежнему может временно сместить союзник с активным приказом; зомби сохраняет прежнюю точку возврата. Если доступных точек не хватило, юнит остаётся на месте и использует те же правила агро и уступки союзникам. Новый приказ отменяет прежний. Атака области не реализована.

Критерии:
- клик по пустой карте не выбирает зомби;
- движение мыши до 8 пикселей остаётся одиночным кликом;
- рамка работает при перетаскивании в любом направлении и снимает выбор с юнитов вне рамки;
- жители не попадают в набор выделения;
- ПКМ после выбора назначает одну общую цель всем выделенным юнитам;
- Shift + ПКМ распределяет выбранных зомби по разным доступным точкам внутри круга радиусом 100;
- новый приказ заменяет старую цель;
- достигшие точек области зомби останавливаются и возобновляют агро после задержки 0,3 секунды;
- если юнит не выбран, ПКМ не вызывает ошибку;
- координаты мыши переводятся из экранных координат в мировые, особенно после добавления камеры.

## 7. Движение зомби

### Состояния
- `IDLE` — нет активной цели, зомби стоит.
- `MOVING` — зомби движется к цели.
- При достижении допустимой окрестности обычной цели зомби останавливается и возвращается в `IDLE`; автоматическое агро возобновляется после задержки 0,3 секунды. При достижении цели приказа области зомби останавливается в режиме удержания позиции и не возобновляет агро до получения нового приказа.

### Данные
- текущая позиция;
- целевая позиция;
- скорость;
- допустимое расстояние до цели;
- статус движения.

Начальные числовые значения временные и должны проверяться в игре.

### Ожидаемое поведение
1. При запуске зомби неподвижен.
2. После приказа получает цель и начинает движение.
3. При достижении цели останавливается.
4. Новый приказ во время движения меняет цель.
5. У цели не должно быть дрожания или бесконечного микродвижения.
6. При препятствии зомби должен обходить его навигацией или корректно сообщать о недоступной цели; он не должен проталкиваться сквозь стену.

## 8. Навигация и препятствия

Текущий прототип использует физическую коллизию для предотвращения прохождения сквозь препятствие и навигационную область с исключённой геометрией препятствия для расчёта обходного пути. `NavigationAgent2D` рассчитывает путь; скрипт зомби каждый кадр движения задаёт желаемую скорость к следующей точке пути. Включённое локальное избегание рассчитывает безопасную скорость через `velocity_computed`, и только callback применяет её к `CharacterBody2D` через `move_and_slide()`. Для прямоугольной физической формы зомби 20 × 32 радиус избегания составляет 19 единиц — достаточно, чтобы учитывать углы прямоугольника. Дистанция соседей — 80, максимум соседей — 16, временной горизонт агентов — 1 секунда. Физические коллизии сохранены как окончательное ограничение движения. При отсутствии цели желаемая и фактическая скорости обнуляются, чтобы избегание не продолжало движение самостоятельно.

Навигационная область и физическая коллизия продолжают отвечать за неподвижные препятствия; локальное избегание предназначено для движущихся зомби и не заменяет навигацию. Если приказанный зомби встречает свободного союзника, союзник временно смещается вбок, а приказанный юнит ждёт, пока траектория освободится; после прохода союзник медленно возвращается к сохранённой позиции. Физические коллизии сохраняются. Это локальная уступка свободных зомби, а не общее решение для узких проходов, неподвижных целей и любых скоплений. Проверять встречное движение и группы вручную в Godot 4.7.2: само наличие avoidance-настроек не гарантирует бесконфликтное движение во всех геометриях.

Для приказа области карта детерминированно генерирует точки в пределах радиуса 100, сопоставляет их с navmesh, исключает точки с физическим пересечением и проверяет достижимость пути отдельно для каждого зомби. Индивидуальные позиции выбираются без наложения прямоугольных физических форм; при нехватке свободных позиций юнит остаётся на месте и удерживает его. Локальное избегание и физические коллизии продолжают работать при движении к назначенным позициям; это не является обещанием успешного размещения в тесной или частично недоступной области.

## 9. Поток команды

Для текущего прототипа поток команды относится только к приказу перемещения одного выбранного зомби:

```text
Ввод мыши
   ↓
Проверка выбранного юнита
   ↓
Получение координат цели в мире
   ↓
Передача приказа зомби
   ↓
Обновление цели движения
   ↓
Движение и остановка
```

Этот поток описывает реализованное перемещение к одной точке, а не окончательную модель исполнения будущих приказов. Будущее выполнение приказа не должно сводиться к постоянному прямому движению монстра к одной точке: оно должно допускать смену приоритетной цели и повторный выбор действия.

Область приказа, задающая пространство выполнения задачи, и область приоритетных целей, влияющая на выбор целей, должны оставаться разными понятиями. Навигация рассчитывает путь к выбранной цели, но сама по себе не выбирает цель и не определяет поведение существа. Локальная реакция на непосредственную угрозу должна быть согласована с основным приказом и, когда это уместно, позволять существу вернуться к его выполнению.

Это архитектурные ориентиры, а не готовая схема классов или требование немедленно реализовать менеджер приказов, иерархию ИИ либо конечные автоматы. Не создавать отдельный `OrderManager`, пока приказ не понадобится нескольким типам юнитов или иное конкретное требование не оправдает его. Системы выбора, боя, заражения, поведения деревни, миссии и метапрогрессии добавляются по мере необходимости.

### Текущая модель боя и заражения
Обнаружение цели, приближение, бой и применение результата — логически различимые этапы. Заражение не запускается обнаружением или началом боя: отдельная случайная проверка выполняется при каждом успешном попадании зомби по живому жителю, который ещё не заражён.

Для будущей модели достаточно различать концептуальные состояния:
- житель: жив и доступен для взаимодействия; заражается; обращён и перешёл под управление; погиб, оставив тело;
- монстр: действует/участвует в столкновении; погиб и более не действует.

Скрипт жителя реализует `AVAILABLE`, `IN_COLLISION`, `TRANSFORMING`, `CONVERTED` и `DEAD`. Один повторяющийся таймер у каждого атакующего зомби обрабатывает его удары раз в секунду; каждый удар наносит урон жителю и выполняет проверку шанса заражения 0.15. Житель имеет отдельный таймер атаки с интервалом 1 секунда и за один удар атакует только одного участника: первого живого зомби в порядке присоединения к столкновению. При этом все атакующие зомби продолжают наносить свой урон жителю независимо. Максимальное здоровье по умолчанию: 120 у зомби и 100 у жителя; урон зомби — 20, жителя — 15. При успешной проверке заражения житель немедленно переходит в `TRANSFORMING`, и его собственный одноразовый `TransformationTimer` запускается на 2 секунды. После запуска новые проверки прекращаются. Если урон обнуляет здоровье до заражения, житель переходит в `DEAD`, бой завершается и на нём показывается красный X. Если превращение уже запущено, нулевое здоровье не вызывает окончательную смерть: бой прекращается, но таймер продолжает работать. Каждый атакующий может отдельно покинуть бой по приказу или смерти; оставшиеся участники продолжают атаковать. Когда все участники ушли, атаки прекращаются, но `TRANSFORMING` сохраняется. По таймеру житель однократно переходит в `CONVERTED` и испускает сигнал; карта регистрирует результат, создаёт на его месте существующую `zombie.tscn` и удаляет прежнего жителя. Новый зомби входит в `player_units` и использует общие управление, навигацию и агро. Значения боя и заражения временные, настраиваются через экспортируемые параметры и будут балансироваться.

Житель хранит список участников активного боя. Любой живой зомби в дистанции может присоединиться к бою, если житель ещё не превращён и бой активен; каждый участник имеет только собственный таймер атаки по жителю. Житель своим отдельным таймером атакует только первого живого зомби в списке, а не всех участников сразу. Выход или смерть одного зомби удаляет только его из списка и останавливает его таймер; оставшиеся атакующие продолжают бой. Если участников больше нет до начала заражения, житель возвращается в `AVAILABLE`. Если он уже в `TRANSFORMING`, состояние и таймер сохраняются независимо от наличия участников.

Физическая маска каждого зомби, в том числе созданного после превращения, включает слой зомби и препятствий. Поэтому экземпляры из тестовой сцены и динамически созданные зомби физически блокируют друг друга. Зомби, преследующий уже занятого жителя, продолжает приближаться и при достижении дистанции взаимодействия присоединяется к его бою, запуская собственный таймер атаки. После завершения приказа игрока поиск агро возобновляется через 0,3 секунды.

### Учёт жителей тестовой миссии
Скрипт тестовой карты при запуске находит сцены жителей, сохраняет их исходное количество и подключается к сигналам завершённого превращения и окончательной смерти. Смерть до запуска превращения испускает `died` один раз; переход в `CONVERTED` испускает `converted` один раз. Карта регистрирует уникальные идентификаторы заражённых и погибших отдельно, не допуская двойного учёта одного жителя. Общее количество фиксируется на старте миссии; созданные зомби не добавляются в список жителей. Житель, погибший до превращения, остаётся в исходном общем количестве и засчитывается как уничтоженный, но не как заражённый. Нулевое здоровье во время `TRANSFORMING` прекращает столкновение, однако не регистрирует смерть и не отменяет завершение превращения.

Временная цель тестового прототипа — заразить или уничтожить не менее 80% жителей. Счётчик прогресса — размер объединения уникальных заражённых и погибших жителей; требуемое целое количество рассчитывается округлением вверх: `ceil(total_residents * 0.80)`. Интерфейс отдельно показывает число заражённых, убитых, ещё не учтённых жителей и общий прогресс. При нуле жителей победа не объявляется, а интерфейс явно сообщает, что цель выполнить невозможно. Победа фиксируется один раз; поражение и блокировка управления не реализуются. Порог 80% относится к тесту и в будущем может задаваться отдельно для каждой миссии.

Интерфейс размещён в `CanvasLayer`, а его элементы игнорируют мышь, чтобы оставаться закреплёнными к экрану и не перехватывать ввод игрового мира.

В будущей реализации следует отдельно определять (1) исход столкновения и выживание участвующих сторон и (2) судьбу жителя после взаимодействия — например, его гибель или заражение. Не объединять эти решения в одну проверку или вероятность. Характеристики обеих сторон, типы существ, способности и эволюционные формы могут влиять на исход; раса монстра и открытые метапрогрессией возможности могут отдельно влиять на судьбу жителя. Конкретные формулы и баланс не определены.

Применение исхода должно быть однократным: после фиксации результата тот же процесс не может повторно изменить состояния или повторно учесть участника. Зомби с нулевым HP прекращает движение, преследование, взаимодействия, атаки и выполнение приказов, удаляется из `player_units`, отключается от физических коллизий и от локального навигационного избегания, чтобы оставшееся видимым тело не считалось неподвижным агентом. Житель, погибший до заражения, прекращает бой, становится недоступным для агро и отключается от коллизий. Превращение в процессе не считается окончательной смертью при нулевом HP. Персонажи не удаляются автоматически при смерти; над ними отображается красный X. Живые зомби и жители рисуются поверх погибших; полосы HP скрываются при смерти. У живых полосы HP рисуются без физических узлов: зелёные у зомби, красные у жителей, заполнение соответствует отношению текущего HP к максимальному.

Сложные исходы столкновений, расчёт вероятности смерти или иных исходов, броня и универсальная боевая архитектура пока не реализованы. Текущие здоровье, взаимный урон и шанс заражения при ударе — временная минимальная механика прототипа; дальнейшее развитие должно сохранять однократное применение исхода и не требовать переписывания навигации и приказов.

## 10. Временная визуализация

- зомби — цветной круг/спрайт-заглушка;
- цель — маркер;
- препятствия — прямоугольники;
- выбранный юнит — контур или другой индикатор.

Финальные спрайты, анимации, эффекты и освещение отложить до проверки основного цикла управления.

## 11. Граничные случаи

Проверить:
- команда без выбранного юнита;
- цель совпадает с текущей позицией;
- новый приказ выдан до завершения предыдущего;
- цель за препятствием;
- цель недоступна для навигации;
- отсутствует ожидаемый узел;
- в сцене случайно нет зомби;
- после добавления камеры экранные и мировые координаты не совпадают.

Невалидный приказ должен обрабатываться предсказуемо: безопасно игнорироваться или приводить к диагностическому сообщению. Не скрывать реальные ошибки пустыми обработчиками.

## 12. План реализации и критерии приёмки

Технические этапы тестовой карты, зомби-заглушки, выбора, движения и навигации составляют уже созданную основу прототипа. Их критерии из разделов 6–11 остаются регрессионными проверками для последующих изменений, но не определяют следующий приоритет разработки.

Следующий этап следует предварительной последовательности из GDD, раздел 15: зафиксировать минимальный игровой цикл; добавить простого жителя и базовое обнаружение им угрозы; реализовать простейшее автономное поведение зомби; создать первое взаимодействие между ними; добавить простую боевую или конверсионную механику; завершить цикл проверяемым условием окончания тестовой миссии. Конкретный технический объём каждого шага уточняется непосредственно перед его реализацией.

Каждую новую часть следует проверять на небольшой тестовой сцене. Не добавлять общую систему приказов, сложную архитектуру поведения или расширенный интерфейс без конкретной игровой ситуации, на которой можно проверить необходимость этой системы.

## 13. Работа с ИИ и Git

Каждый запрос ИИ должен содержать контекст игры, текущую цель, имена существующих файлов, требуемое поведение, критерии приёмки и ограничения. Просить перечислить файлы до изменения и объяснить способ проверки после.

Рабочий цикл:
1. проверить `git status`;
2. дать ИИ одну ограниченную задачу;
3. просмотреть изменения;
4. запустить игру;
5. проверить критерии;
6. исправить ошибки;
7. после успеха создать commit.

Не принимать утверждение ИИ «всё работает» без запуска и проверки.

## 14. Первый запрос для ИИ-кодинга

Ниже приведён исторический пример запроса для первоначальной настройки проекта; он не является планом следующей задачи.

> Работаем над 2D-игрой I'm a Monster на Godot 4 и GDScript. Прочитай `docs/game_design.md` и `docs/technical_design.md`, если они доступны. Сейчас выполняем только этап 1: создать минимальную главную сцену и тестовую карту. Не реализовывай зомби, движение, боёвку, жителей или UI. Используй простую заглушку фона. Сначала перечисли файлы, которые собираешься создать или изменить, затем внеси только необходимые изменения. Не меняй настройки проекта без необходимости. В конце объясни, как запустить сцену и проверить результат. Критерий приёмки: проект запускается и показывает тестовую карту без ошибок.

Этот запрос сохранён как пример оформления задачи, а не как инструкция к текущему прототипу.
